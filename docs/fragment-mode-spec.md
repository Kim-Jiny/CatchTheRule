# 조각 숫자 모드 (track: "fragment") 명세

세 구현(콘텐츠 생성기 Python / iOS Swift / Android Kotlin)이 **같은 규칙**을 쓰도록 정의한 단일 명세. 홈 허브/해금 게이트/캠페인 흐름/타임어택 믹스는 기존 모드(숫자 만들기 `target`, 성냥개비 `match`)와 같은 방식으로 붙인다. 참고 메모리: `catchtherule-target-track`, `catchtherule-match-track`.

## 1. 게임
7세그먼트 디지털 숫자(1~4자리)를 **여러 장의 조각으로 쪼개** 한 장씩 **일정 시간마다 돌아가며** 보여 준다(무한 반복). 플레이어는 머릿속에서 조각을 합쳐 **완성된 숫자**를 입력한다. 한 장만 보면 숫자가 아니거나, 다른 숫자처럼 보이는 함정이 있다.
- 글자가 없으므로 번역이 필요 없다(프롬프트/규칙 캡션만 번역).
- 입력은 **직접 입력(키패드, `keypad`) 전용**(보기 고르기 없음, 2026-10-15 사용자 결정). 정답 판정은 `answer` 문자열 비교(기존과 동일).

## 2. 데이터 스키마 (shared/content/puzzles.json 항목)
```
{"id":"fg5_s03","type":"fragment","track":"fragment","chapter":5,"order":3,
 "frames":[ ["ab","","g"], ["","bc","d"], ["f","","a"] ],   // frames[f][d] = f번째 장에서 d번째 자리(왼쪽부터)에 켜지는 획 문자열(a~g 알파벳 순서 무관)
 "combine":"or",                 // "or" | "xor"
 "frameMs":1500,                 // 한 장을 보여 주는 시간(ms)
 "answer":"385",                 // 합친 결과 숫자(선행 0 없음)
 "inputType":"keypad","choices":null,
 "hints":{ko:[3],en:[3],ja:[3],zh:[3],es:[3],fr:[3],de:[3]},
 "explanation":{ko:"...",...7개 언어}}
```
- 모든 `frames[f]` 의 길이 = 자릿수(`answer` 길이). 각 장의 각 자리는 빈 문자열("")일 수 있다.
- 앱 모델: `frames: [[String]]?`, `combine: String?`, `frameMs: Int?`, `isFragment = frames 비어있지 않음`.

## 3. 합성 규칙 (생성기·앱 공통, 핵심)
세그먼트: 성냥개비 명세와 같은 7개 `a(위 가로) b(오른쪽 위) c(오른쪽 아래) d(아래 가로) e(왼쪽 아래) f(왼쪽 위) g(가운데 가로)`.
숫자 패턴: `0:abcdef 1:bc 2:abdeg 3:abcdg 4:bcfg 5:acdfg 6:acdefg 7:abc 8:abcdefg 9:abcdfg`.
- **or**: 한 자리의 최종 켜진 획 = 모든 장에서 그 자리에 나온 획의 **합집합**. 같은 획이 여러 장에 나와도 된다.
- **xor**: 최종 켜진 획 = **홀수 번 나온 획**(두 번 나오면 사라짐). 최종 켜지지 않는 획도 짝수 번(0 또는 2번) 나올 수 있다(함정).
- 합성 결과 각 자리는 반드시 유효 숫자 패턴이어야 하고 그 숫자들을 이어 붙인 것이 `answer`. 

## 4. 화면/조작(앱)
- 상단 프롬프트 `fragment_prompt`. xor 퍼즐이면 그 아래 작은 캡션 `fragment_rule_xor`(규칙이 헷갈리지 않게; or 퍼즐은 캡션 없음).
- **디스플레이 카드**: 자릿수만큼 큰 7세그먼트 숫자를 가로로 배치. **꺼진 획은 흐린 고스트**(위치를 알 수 있게)로, 현재 장에서 켜진 획만 **장 색 + 글로우**로 밝힘. 장 색(고정 순서): 1장 시안 #18C8FF, 2장 핑크 #FF5C8A, 3장 앰버 #FFB020, 4장 그린 #3DDC97.
- **순환**: 1장 → 2장 → … → 마지막 장 → 1장 …, 한 장당 `frameMs`, 장 전환은 짧은 크로스페이드(약 120ms; **깜빡임이 빠르지 않게** 최소 `frameMs` 600 이상). 카드 아래에 **장 번호 점 표시**(현재 장 점이 해당 색으로 채워지고 진행 바가 차오름).
- 입력: 키패드(자릿수 이상 입력 불가 — 기존 `typed.count < 4` 규칙은 4자리와 호환) 또는 4지선다. 오답이면 기존 흔들림 처리. 정답이면 기존 정답 처리(배지, 별, 지연 후 advance, 전면광고).
- 문제가 바뀌면(퍼즐 id 변경) 순환을 처음 장부터 다시 시작. 화면이 가려지거나 앱이 백그라운드면 순환 정지(전력/접근성), Reduce Motion 이어도 순환은 유지(크로스페이드만 즉시 전환).
- 힌트 3개는 기존 힌트 UI 재사용(텍스트).
- 모드 칩/아이콘/색: 모드 키 `fragment`, 이름 `mode_fragment`, 챕터 제목 `fragment_chapter_1..14`, 모드 색 **#A3E635(라임)**, 아이콘 iOS `square.stack.3d.up.fill`, Android `Icons.Filled.Layers`. 홈 그리드는 모드가 홀수(7)가 되므로 **마지막 카드는 2열을 모두 차지(가로 꽉)** 하게 한다.
- 해금 게이트는 기존과 공유. `PuzzleStore.trackOrder` 맨 뒤에 `"fragment"` 추가.
- **타임어택 믹스**에도 포함: 별도 UI 없이 기존 숫자 문제 경로(`SequenceDisplay` + keypad/choices)가 이 모드의 디스플레이를 그리면 된다(각 모드 앞쪽 절반 챕터 규칙 그대로).

## 5. 난이도 사다리 (14챕터 × 6문제, id `fgN_sMM`)
| 챕터 | 자릿수 | 장 수 | frameMs | 합성 | 입력 | 비고 |
|---|---|---|---|---|---|---|
| 1~2 | 1 | 2 | 2000 | or | keypad | 한 자리, 두 조각 |
| 3~4 | 2 | 2 | 1800 | or | keypad | |
| 5~6 | 3 | 3 | 1500 | or | keypad | |
| 7~8 | 3 | 3 | 1200 | or | keypad | **함정 필수**: 어떤 한 장이 정답과 다른 유효 숫자처럼 보이는 자리가 있다 |
| 9~10 | 4 | 3 | 1000 | or | keypad | 같은 획을 여러 장에 중복 등장(or) |
| 11~12 | 3 | 2~3 | 1200 | **xor** | keypad | `fragment_rule_xor` 캡션 표시, 짝수 번 나와 사라지는 획(노이즈) 포함 |
| 13~14 | 4 | 3~4 | 1000→700 | xor(+or 섞기) | keypad | 4장, 노이즈 획 다수, 함정 |
- 챕터 안 order 1→6 으로 점점 어렵게(노이즈 획 수, 함정 수, frameMs 감소). 모든 퍼즐은 정답이 유일(합성 규칙이 결정적이므로 자동). 같은 `answer`+`frames` 중복 금지, 챕터 내 정답 숫자 중복 최소화.
- 함정 판정(생성기): "어떤 장의 어떤 자리"가 그 장만 보면 유효 숫자 패턴이면서 정답 자릿수와 다른 숫자.

## 6. 힌트(3개, 7개 언어)·설명
1) 규칙 요령: or → "모든 장에 나온 획을 한 숫자 위에 겹쳐 보세요." / xor → "두 번 나온 획은 사라진다는 걸 기억하세요."
2) "첫 번째 자리의 숫자는 N이에요." (answer[0])
3) "각 자리 숫자를 모두 더하면 S예요." (자릿수 합) — 1자리 퍼즐이면 "N은 홀수/짝수"처럼 다른 단서로 대체(생성기 재량, 7개 언어 번역).
`explanation`: 언어 중립 "385" 와 함께 "3 + 8 + 5"가 아니라 그냥 정답 숫자 문자열(예: "385").

## 7. 테스트 벡터
`scripts/fragment_test_vectors.json` — 생성기가 만든다: `{"format":..., "combine_cases":[{"combine":"or|xor","frames":[[...]],"result":"385" or null(invalid)}], "samples":[실제 퍼즐 10개 요약]}`. 플랫폼 구현이 합성/유효성 판정(디스플레이에서 최종 숫자 계산이 필요하진 않지만, 힌트·디버그 검증용)과 JSON 디코딩을 검증하는 데 쓴다.
